## What B06 is on this branch

Four optional request keys plus one marker, projected by `buildRustV2Options`
(`web/src/lib/rustPipelineRuntime.ts`) as `maximum_duration_policy`,
`maximum_duration_disposition`, `maximum_duration_threshold_source`,
`maximum_duration_threshold_ns` (decimal string, never a JS number) and
`long_duration_threshold_explicit`, with the browser-derived legacy companions
`b06_legacy_threshold_hours_canonical` / `b06_legacy_threshold_ns_canonical`. Five legal presence
shapes (`rust/chronicle_chrono_kernel_wasm/src/b06_maximum_duration.rs::select_shape`, mirrored
by `web/src/lib/maximumDurationVector.ts`); the generic policy qualifies an episode strictly
above the threshold (`d > T`) and applies one of four dispositions; truncation stops at
`start + T` with `effective_endpoint_reason = maximum_duration_truncation_boundary`.

With every B06 key absent the golden outputs are byte-identical to `01be6d2` (kernel golden
suite and the B06 omission fixture check). The receipt travels on the manifest as
`processingSummary.maximumDurationReceipt`.

## Refusals and where they surface

| Case | Preflight (`maximum_duration_applicability_json`) | Execution |
|---|---|---|
| `chronicle_observed_close_rejection_v1` × any non-`fused_matcher` strategy | `refused`, `maximum_duration_policy_incompatible_with_reconstruction_strategy` | `pipeline_options_invalid:b06=…` before any tracked query |
| `b12_adaptive_participant` | `refused`, `adaptive_maximum_threshold_provider_unavailable` | same |
| malformed vector (shape / threshold grammar / legacy companions) | `refused`, `maximum_duration_request_shape_invalid` etc. | same, and the opener-set preflight rejects it too |

**Defect found by the campaign and fixed here:** the product (and the harnesses) run the
opener-set preflight before the B06 preflight. `opener_set_applicability_json` validated the
whole request, so a *legal but refused* B06 vector raised the raw
`pipeline_options_invalid:b06=…` error and the typed refusal was never reached — the browser
would have shown "opener-set preflight failed: …" instead of "Maximum-duration policy X cannot
run with the selected settings (reason)". Fix: `pipeline_v2::validate_pipeline_v2_options_with`
takes a `MaximumDurationValidation` scope (`Complete` for execution/review, `MalformedOnly` for
the opener preflight, `Skip` for the B06 preflight, which reports every B06 outcome as data);
`RuntimeRequest::validate_fields_with` threads it. Pinned by
`refused_maximum_duration_vectors_pass_the_opener_preflight_and_surface_through_the_b06_preflight`
(runtime) and `maximum_duration_validation_scopes_separate_malformed_vectors_from_typed_refusals`
(kernel); the `@smoke @opfs` e2e in `web/e2e/app.spec.ts` asserts the browser-facing message for
`b12_adaptive_participant`.

## Second defect the gate found: manifest shape

The new `@smoke @opfs` B06 e2e failed on chromium and firefox with
`runtime manifest contract violation at
manifest.processingSummary.maximumDurationReceipt.excludedEpisodes[0].rawStartTimestampNs:
expected a safe integer`. The manifest embedded the whole `MaximumDurationEvidence`, so the
participant-level excluded lineage — participant ids and i64 nanosecond timestamps — crossed the
browser boundary as JSON numbers. Two things were wrong: PHI-safety (the manifest is the
aggregate-only surface; B04 keeps its lineage in a content-addressed artifact) and exactness
(an i64 above 2^53 cannot be a JSON number).

Fix, mirroring B04: `RuntimeProcessingSummary.maximum_duration_receipt` and the review manifest
now carry `MaximumDurationReceipt` (the aggregate) instead of `MaximumDurationEvidence`; the
excluded lineage stays in the `maximum-duration-receipt-json` artifact (whole evidence, JCS),
bound to the manifest by `excludedLineageDigest`; and
`MaximumDurationApplicability.threshold_ns` is a canonical decimal string on every surface, so a
threshold of `i64::MAX` travels exactly. Pinned by
`maximum_duration_manifest_carries_the_aggregate_receipt_and_the_artifact_carries_the_lineage`
(runtime, exercising `9223372036854775807`) and by the e2e's own manifest assertions.

## Third defect the gate found: a refusal erased its own shape

Once the browsers could launch, that same `@smoke @opfs` e2e failed in chromium and firefox
with `runtime manifest contract violation at maximumDurationPreflightDecision: explicit request
resolved to the omitted shape` instead of the adaptive refusal message. The refusal reason was
right; the shape was not.

`resolve_maximum_duration` built the correct applicability — `explicit_generic_adaptive`, with
the requested policy, disposition and source — and then returned `Err(reason)`, discarding it.
`maximum_duration_applicability` caught that error and reconstructed an applicability with a
hardcoded `shape: OmittedLegacy`. Both conditional refusals therefore reported an explicit
selection as the omitted shape, and `preflightMaximumDuration`
(`web/src/lib/rustPipelineRuntime.ts`) rejects exactly that combination — so the contract
violation masked the typed refusal the researcher is supposed to see.

Fix: the resolution body moved into `resolve_maximum_duration_parts`, which returns
`Ok((None, applicability))` for the two applicability refusals (a legal shape this build cannot
run) and `Err(reason)` only for a malformed vector (which never resolved to a shape, so the
omitted-shape reconstruction below it stays correct). `resolve_maximum_duration` keeps its
existing signature and still errors on every refusal, so no execution path changed. Pinned by
`applicability_refusals_report_the_selected_shape_not_the_omitted_one` (kernel) and a shape
assertion added to the `b12_adaptive_participant` arm of
`web/src/lib/maximumDurationVector.test.ts`.

Both this and the preflight-ordering defect above are the same class: the unit and campaign
tests asserted `refusalReason` and never `shape`, so only the browser's own contract check
caught it.
