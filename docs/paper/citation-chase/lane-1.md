# Citation chase — Lane 1 (Winklbauer & Batinic reference entries 1–10)

Audit of what each cited study **declares** about turning raw device events into usage
numbers. "NOT STATED" means the paper is silent — that is a finding, not a lookup failure.
Retrieval was limited to `WebFetch` and `curl`; no browser automation was used. Pages that
require JavaScript, or that returned 403/503 to a plain HTTP client, are recorded as
unavailable.

Ladder rungs (dossier §7.1): **4** = raw platform event log with declared semantics;
**3** = app-level event-logging research app; **2** = screen-on/off logging only;
**1** = vendor aggregate (iOS Screen Time, Digital Wellbeing, battery stats).

## 1. Andrews, Ellis, Shaw & Piwek (2015) — Beyond self-report: tools to compare estimated and real-world smartphone use

- **Instrument and ladder rung.** **Rung 2** — screen/interactive-state logging only. Bespoke
  Android app built with **Funf in a Box**. Verbatim (Method → Materials): *"We developed an
  Android smartphone app using Funf in a Box [11]. Apps collecting data from Android devices
  are generated by selecting sensors, and specifying sampling frequency. We selected the screen
  on/off option, resulting in a small app that records a timestamp when a use starts and ends."*
  Critically, the authors report the sensor did not measure what they intended (Method →
  Procedure): *"However, during testing, it was discovered that the on-off sensor actually
  measured whether the phone was in an interactive state, which included activities such as
  phone calls and listening to music, commonly done with the screen switched off."*
- **Session threshold.** **NOT STATED** as an inactivity/merge threshold. The only threshold in
  the paper is a post hoc *classification* cutoff (Results → Objective Data): *"We classify
  'checks' as uses up to 15 seconds in duration."* No justification beyond a lab timing
  observation (*"In the lab, mean time taken to unlock the phone and read a short message was
  8.42s (SD = 1.53)"*).
- **Episode reconstruction rule.** Effectively **none is needed and none is given** beyond the
  sensor's own on/off pairing: *"Our app simply recorded a timestamp when the phone became
  active, and a second when this interaction ended."* Processing is delegated to unnamed
  vendor scripts plus supplied code (Method → Procedure): *"Data from the app were converted
  into a comma separate values file using Funf processing scripts. This file was further
  processed using source code to calculate descriptive statistics and barcode visualisations."*
  No rule is stated for splitting, merging, or capping episodes; long episodes are explicitly
  **retained**: *"As it is impossible to be sure that all long durations were because of this,
  we retain these data in all analyses."*
- **System-app / launcher filtering.** **NOT STATED** — not applicable at this rung; the
  instrument records no app identity at all.
- **Window, exclusions, aggregation.** 14 days (*"We use descriptive statistics for the first 14
  days of the study throughout"*). 29 recruited; *"Two participants were excluded as they had
  technological problems partway through the study, while four additional participants were
  excluded from the analysis for not providing all self-report estimates"* → 23 analysed.
  Aggregation is an explicit **median-then-mean** two-stage rule: *"we use median values when
  calculating an average values for each day, as this is a more accurate summary of the average
  use length. We then use these values to calculate the mean use length for each participant."*
  Episodes crossing a time-of-day boundary are assigned by start time: *"phone uses that spanned
  two time windows … was allocated to the time period in which it originated."*
- **Availability.** Analysis code is published as supporting information (S1 Appendix, MATLAB
  2014b+). *"Data Availability: All relevant data are within the paper and its Supporting
  Information files."* No repository URL; the code covers descriptives/visualisation, not
  event-to-episode reconstruction (there is none to cover).

**Access:** Full text, via the PLOS ONE open-access article page (`journals.plos.org`, curl).

- **Window, exclusion rules, aggregation.** From the abstract: *"a sample of 93 University

- **Availability.** The abstract advertises a Python processing script; no repository URL
  appears in the abstract or on the UvA-DARE landing page I retrieved.
- **Transcription note.** The reference list dates this 2022; the Sage issue is **41(4), 2023**

## 4. Beierle, Probst, Allemand, Zimmermann, Pryss, Neff, Schlee, Stieger & Budimir (2020) — Frequency and duration of daily smartphone usage in relation to personality traits

**This is the single most important entry in the lane.** It is the only Rung-4 study here, it
explicitly states that a reconstruction heuristic exists, and it declares none of its contents.

- **Instrument and ladder rung.** **Rung 4** — the Android system app event log, via the
  research app **TYDR (Track Your Daily Routine)**, an Android app in the Google Play store.
  Verbatim (§2.5): *"We used the Android system's app event log to estimate the user's
  smartphone usage sessions. Each time a user opens or closes an app, the Android system
  records an event. Given the appropriate permission by the user, TYDR can access these logs
  and store them in the TYDR database."* Footnote 7 narrows the event vocabulary consumed:
  *"Additionally, other app events are recorded for other types of actions of apps. For the
  usage session estimation, we only need the events for opening an app to the foreground and
  closing it."*
- **Session threshold.** **NOT STATED.** No inactivity gap, no minimum duration, no maximum
  duration, no proximity/merge interval anywhere in the paper. Note the reported range —
  *"lasting for 221 seconds on average (median = 164, range 2 to 4198)"* and, for the whole
  installed base, *"range 2 seconds to 12 hours"* — which implies neither a floor nor a cap was
  applied.
- **Episode reconstruction rule.** **Acknowledged to exist; contents entirely undeclared.**
  Verbatim (§2.5): *"We define a smartphone usage session as the time window in which a user was
  actively using the phone. Each session starts with turning on the display and ends with
  turning the screen off."* Then, verbatim: *"We implemented a heuristic for estimating actual
  usage sessions, including background app removal, detection, and imputation of missing events
  that were not recorded correctly. Based on 40,140,665 app events, our heuristic yielded
  1,826,060 usage sessions in total by the 526 users in our sample."* No parameters, no
  pseudocode, no citation to a specification, no appendix. A 40.1M-event → 1.83M-session
  transformation — a 22:1 reduction — rests entirely on the word "heuristic". This is the
  undeclared researcher degree of freedom the paper argues for, in its purest observed form.
- **System-app / launcher filtering.** **Named but not specified.** "background app removal" is
  the only mention; no list, no package-name criterion, no launcher handling.
- **Window, exclusion rules, aggregation.** Data collected 14 Oct 2018 – 10 Sep 2019; *"On
  average, users provided data across 48 days"* (SD = 63.2, range 2–304 days) — i.e. an
  unbalanced, self-determined window with no minimum-days rule. Inclusion: *"Our sample – those
  that fulfilled the conditions of having filled out the Big Five questionnaire and having at
  least 1,000 app event log entries associated with them – contains 526 users."* The 1,000-event
  floor is justified only in footnote 6: *"We considered 1,000 app event log entries to be enough
  to give some insight into the user's phone usage behavior."* Aggregation is to the day and uses
  the **mean**: criterion variables are *"number of screen wakeups per day and session duration"*,
  modelled as *"mean session duration per day"* in a random-intercept/random-slope MLM.
- **Availability.** **No code and no data are released.** No data-availability statement, no OSF
  or GitHub link; only a supplementary table of intercorrelations and a gender × personality
  table. The session-estimation heuristic is therefore unreproducible in principle.

**Access:** Full text, via the Digital Psychology (Facultas) diamond-OA PDF
(`ejournals.facultas.at/…/1821/1581`, curl → pdftotext).

## 6. Bradley & Howard (2023) — Stress and mood associations with smartphone use in university students

- **Instrument and ladder rung.** **Rung 1 (vendor aggregate), transcribed by humans from
  screenshots.** Verbatim (Measures → Device-logged reports of screen time): *"At each weekly
  survey, available from Sunday through Tuesday morning, participants were asked to upload two
  screenshots from their Screen Time application (a preinstalled app located in an iPhone's
  settings; see Fig. 1). The Screen Time application provides a report showing how the device
  was used, including names of apps that were opened, hours of use (global and app specific),
  and numbers of times the device was picked up (Apple Support, 2021)."* Extraction is manual:
  *"Volunteer research assistants extracted six measures of screen use from each person's
  screenshots."*
- **Session threshold.** **NOT STATED.** No threshold appears anywhere; sessions are Apple's
  "pickups", defined only by quoting Apple's own gloss — *"overall daily phone pickups (i.e.,
  instances of the user interacting with an app on their device after it was sitting idle)"*.
  The idle interval that qualifies a pickup is Apple's, undisclosed, and unversioned.
- **Episode reconstruction rule.** **NOT STATED, and structurally absent** — there is no event
  log in this pipeline at any stage. The only transformation the paper declares is a unit
  conversion: *"Weekly totals were converted to daily averages."*
- **System-app / launcher filtering.** **NOT STATED.** iOS Screen Time's own inclusion rules are
  not discussed. The authors do impose a *post hoc* app **classification** scheme (entertainment
  and gaming / social networking / information, reading and productivity / other; social
  networking split into social media and text messaging for the access measures), with
  classifications posted to OSF — but that is categorisation, not filtering.
- **Window, exclusion rules, aggregation.** Up to 12 weekly surveys across the fall 2020
  semester; the weekly cadence is chosen by the instrument, not the design: *"We selected this
  time frame because iPhone Screen Time summaries are available in weekly intervals."* N = 187,
  973 weekly responses, 860 with at least one usable screenshot. Screenshot-level exclusion is
  declared: *"A screenshot was deemed unusable if it did not include a past-week summary (e.g.,
  the screenshot contained only 1–2 days' worth of screen use) or was a duplicate."* Missing-data
  handling is flagged as unplanned: *"Note that we did not include a strategy for working with
  missing data within our preregistration, and this strategy was ad hoc."* Aggregation: weekly
  totals → daily averages, analysed in multilevel models (means).
- **Availability.** **Public.** *"All data and materials have been made publicly available via
  OSF and can be accessed at https://osf.io/2gy63/."* Preregistration: https://osf.io/a9xpg.
  Open Data / Open Materials / Preregistration badges. Note that what is public is the
  *transcribed vendor aggregate*, not any raw event log — there is none.

**Access:** Full text, via PubMed Central (`pmc.ncbi.nlm.nih.gov/articles/PMC10491487/`, curl).

## 7. Cernat, Keusch, Bach & Pankowska (2024) — Estimating measurement quality in digital trace data and surveys using the MTMM model

- **Instrument and ladder rung.** **Rung 3 (app-level event logging), operated by a commercial
  vendor, not the authors.** Verbatim (Data and Methods → Data and Experimental Design): *"Data
  for this paper were collected from members of a commercial opt-in online access panel in
  Germany, maintained by respondi/bilendi. … Participants of the additional data collection were
  asked to install a browser plug-in on their personal computers and to download a research app
  to their mobile devices."* And: *"Visits to websites from a device's native browser (i.e.,
  Chrome on Android devices and Safari on Apple devices) as well as the names of the apps that
  participants used (including date, time, and duration of use) were recorded."* The durations
  arrive **pre-computed by the vendor's app**; the authors never see events.
- **Session threshold.** **NOT STATED.** Strikingly, the paper names the threshold problem in the
  abstract-adjacent framing and then does not resolve it for its own data (Introduction/Framing):
  *"As part of this aggregation process, researcher must make decisions regarding the appropriate
  level of aggregation and the interpretation of certain patterns in the digital data (e.g., at
  what threshold does a visit to a website count as having engaged with the content on that
  website)."* No threshold is subsequently declared for the analysis.
- **Episode reconstruction rule.** **NOT STATED for the episode level; the general problem is
  explicitly acknowledged.** Verbatim: *"researchers usually must restructure and aggregate
  logged instances of digital behavior to create useful measures that can be further analyzed."*
  What the paper *does* declare is only the coding and summation step: *"To use the digital trace
  data from the trackers, we coded apps and websites into the five activities measured in the
  survey. We aggregate the data for a period of 30 days before the first interview and created
  two indicators either by summing the number of times they did an activity (count trace data)
  and by summing up the duration of the activities (duration trace data)."* How an "instance"
  with a "duration" came into existence is the vendor's business and is not described. This is a
  measurement-quality paper that measures the quality of a construct whose construction rule it
  does not have.
- **System-app / launcher filtering.** **NOT STATED.** Apps are mapped into five activity
  categories (calls, texting, photos, social media, web browsing); everything outside those five
  is simply not used. No launcher or system-package handling is described.
- **Window, exclusion rules, aggregation.** 30 days of trace data immediately preceding wave 1
  (*"for a period of 30 days before the first interview"*). Survey waves: 30 Aug – 7 Sep 2021
  (2,235 completes of 3,530 invited) and 14–20 Sep 2021 (1,817 of 2,062). Eligibility required
  prior consent to tracking on at least one device; quota sample of German voting-eligible
  adults, explicitly unweighted (*"we … do not weight our data"*). Aggregation is **summation**
  per participant, then log-transformed: *"We took the logs of these measures to create an
  approximately normal distribution."* FIML under MAR for missingness.
- **Availability.** **Partial.** Note 2 verbatim: *"R code can be found here:
  https://github.com/alex-cernat/digital_trace_mtmm. Survey data is publicly available while the
  digital trace data can be requested from ruben.bach@mzes.uni-mannheim.de."* The processing that
  produced the durations is the vendor's and is not released in any form.

**Access:** Full text, via the University of Mannheim MADOC repository PDF (fetched through
WebFetch, extracted locally with pdftotext). Direct curl to MADOC was blocked by an Anubis
proof-of-work challenge; the Sage full text and PDF returned 403.

## 8. Christensen, Bettencourt, Kaye, Moturu, Nguyen, Olgin, Pletcher & Marcus (2016) — Direct measurements of smartphone screen-time

- **Instrument and ladder rung.** **Rung 2 (screen-on/off only), and pre-binned by the vendor
  before the researchers see it.** Verbatim (Methods → Measurement of Smartphone Screen-time):
  *"On September 1, 2014, participants with smartphones were invited to download a mobile
  application ('app') developed by Ginger.io (San Francisco, CA); this mobile app was capable of
  recording screen-time on Android-based smartphones."* And: *"The app recorded screen-time
  continuously as the number of minutes in each hour that the screen was turned on as long as the
  smartphone was not in 'airplane mode' and the app was not actively turned off."* Two of the
  authors were Ginger.io employees; the sensing logic is not described beyond that sentence.
- **Session threshold.** **NOT STATED, and unrepresentable.** The unit of record is
  minutes-per-hour, so no session, episode, or pickup exists in this dataset at all — the
  instrument destroys episode structure at the source.
- **Episode reconstruction rule.** **NOT STATED, and structurally impossible.** The exposure
  variable is defined purely by arithmetic on hour-bins: *"Within the selected 30-day window, the
  overall average screen-time (averaged over all hours in 30 days) and the hourly average
  screen-time (during each hour of the day, averaged over 30 days) were computed for each
  participant."* This is a "direct measurement of screen-time" (its title) with zero declared
  event semantics.
- **System-app / launcher filtering.** **NOT STATED** — not applicable; no app identity is
  recorded.
- **Window, exclusion rules, aggregation.** Data collected 1 Sep 2014 – 30 Sep 2015; the analysis
  window is chosen by an explicit and unusually well-declared missingness rule: *"The amount of
  missing data (due to phone-off, airplane mode, or app-off) in 30-day rolling windows was
  computed and the windows with the minimum level of missing data were identified and selected
  for analysis. In the event of ties, the earliest window with the minimum amount of missing data
  for each participant was selected for analysis. Participants with no screen-time data (100%
  missing data) or less than 30 days of observation were excluded."* n = 653. Per-participant
  aggregation is the **mean**; the sample-level summaries are **medians with IQR** because the
  distribution is skewed (*"Total screen-time over 30 days was a median 38.4 hours (IQR 21.4 to
  61.3)"*). A complete-data sensitivity analysis is reported.
- **Availability.** **Not public.** *"The primary data used for this analysis was provided by the
  Health eHeart Study. Access to Health eHeart Study data for investigation and publication is
  granted through a formal application process that requires peer review."* No processing code.

**Access:** Full text, via the PLOS ONE open-access article page (`journals.plos.org`, curl).

## 10. Dekker, Baumgartner, Sumter & Ohme (2024) — Beyond the buzz: a notification-disabling intervention

- **Instrument and ladder rung.** **Rung 3** — a named third-party Android research app.
  Verbatim (Method): *"Data was collected using a research app (Murmuras) that tracked
  participants' smartphone behavior and sent daily diary surveys, in addition to three larger
  surveys that were administered via an online survey tool."* Android only: *"Participants had to
  use an Android smartphone since the research app was only available for Android."* The app
  yields app-specific usage and per-notification entries; the paper describes no event semantics
  and cites no Murmuras technical documentation.
- **Session threshold.** **NOT STATED.** A phone session is defined **conceptually** but never
  operationally (Measures → Checking Frequency): *"Phone checking is defined as the initiation of
  a phone session, which consists of unlocking the phone, followed by a series of phone
  activities, until the phone is locked again."* No inactivity gap, no minimum duration, no
  handling of screen-off-during-use.
- **Episode reconstruction rule.** **NOT STATED.** The sentence above is the whole of it: a
  definition of what a session *is*, with nothing about how the log produced one. The only
  declared data transformations are (a) the notification count — *"The daily number of
  notifications was computed by adding up all logged notification entries per day"* — and (b) the
  screen-time app exclusion quoted next.
- **System-app / launcher filtering.** **Declared, ad hoc, and outcome-driven — no list.**
  Verbatim (Measures → Screen Time): *"The data included some extreme outliers of people using
  their phone for 22 hours per day. App-specific data showed some apps that typically keep the
  screen turned on, even when the user does not use their phone (YouTube Vanced; Basic
  Daydreams). Therefore, these apps were removed from the general screen time data."* Footnote 3:
  *"To test robustness, analyses for H1 were also done with data including the screen-on apps but
  this did not yield different findings."* Notice the discovery path — a filter adopted because
  the *output* looked wrong, with a two-app list and no general criterion. A separate,
  differently-scoped filter is applied to notifications only: *"We removed notifications that
  were sent by the phone system or by apps that are not installed by the user (e.g., phone
  launcher, alarm)."* So the launcher is filtered out of the notification stream but **not** out
  of the screen-time stream. Note also what was deliberately *not* filtered: *"Still, some extreme
  outliers were present, but these people seemed to use gaming apps extensively and were thus not
  removed."*
- **Window, exclusion rules, aggregation.** 25 days of participation (baseline week, intervention
  week, post-intervention week, plus four transition days); analysis uses the baseline and
  intervention weeks. Five **preregistered** inclusion criteria, quoted in condensed form: install
  the app after the T0 survey; *"participants needed to have at least fourteen days of tracking
  data"*; complete the T1 survey; *"in both weeks, participants had to complete at least four out
  of seven daily surveys"*; and, for the treatment group, *"intervention compliance had to be
  sufficient (i.e., the tracking data shows that the total number of notifications was reduced by
  at least 75% in the intervention week compared to the baseline week)"*. Final N = 205 (114
  treatment / 91 control) from 365 T0 completers. Aggregation is the **mean** in linear mixed
  models, with medians reported descriptively (*"M = 327.43 minutes, SD = 175.48, median =
  294.87, min = 3.48, max = 1270.00"*).
- **Availability.** **Data public, processing code not.** *"The data described in this article are
  openly available on the Open Science Framework at https://osf.io/45q72/."* Preregistered; Open
  Data badge. What is deposited is the analysis dataset — the Murmuras-side event-to-session
  logic is proprietary and undocumented in the paper.

**Access:** Full text, via the Freie Universität Berlin Refubium repository PDF
(`refubium.fu-berlin.de/bitstream/handle/fub188/43549/…`, curl → pdftotext). Taylor & Francis
returned 403 to both curl and WebFetch despite the article being CC BY-NC.

## Lane 1 summary

**Full text obtained: 6 of 10** — entries 1 (Andrews), 4 (Beierle), 6 (Bradley & Howard),
7 (Cernat), 8 (Christensen), 10 (Dekker). Abstract only: 3 (Baumgartner), 5 (Böhmer),
9 (Coyne). Metadata only: 2 (Baumeister). Of the four I could not read in full, exactly **one
is genuinely paywalled** (entry 5, ACM DL, closed everywhere) and one is closed but
non-empirical (entry 2). The other two — entries 3 and 9 — are **open access that a non-browser
client cannot reach**: Sage/pure.uva.nl returned 403/503 and ScienceDirect returned 403. Those
two are re-chaseable, not lost.

**Session threshold declared: 0 of 10.** Not one study in this lane states an inactivity gap, a
minimum session duration, a maximum session duration, or a merge interval. The closest thing in
the entire lane is Andrews et al.'s *classification* cutoff — *"We classify 'checks' as uses up
to 15 seconds in duration"* — which splits already-formed episodes into categories and does not
form episodes at all.

**Episode reconstruction rule declared: 0 of 10.** Broken down by why:
- **1 study says the rule exists and refuses to state it.** Beierle et al. (entry 4): *"We
  implemented a heuristic for estimating actual usage sessions, including background app
  removal, detection, and imputation of missing events that were not recorded correctly."*
  40,140,665 raw Android app events became 1,826,060 sessions through that sentence, with no
  parameters, no appendix, and no code release.
- **3 studies define a session conceptually and stop.** Dekker et al. (entry 10, *"unlocking the
  phone … until the phone is locked again"*), Beierle (also, *"starts with turning on the display
  and ends with turning the screen off"*), and Cernat et al. (entry 7), which names the general
  aggregation-and-threshold problem out loud and then never resolves it for its own data.
- **3 studies outsource the rule to a vendor and never mention it.** Bradley & Howard and Coyne
  (Apple Screen Time), Cernat (respondi/bilendi's research app supplies pre-computed durations).
- **2 studies have no event log to reconstruct from.** Andrews (Funf on/off pairs) and

**Ladder rungs.** Rung 4: **1** (Beierle). Rung 3: **3** (Böhmer — inferred from abstract and
flagged as unconfirmed; Cernat; Dekker). Rung 2: **2** (Andrews, Christensen). Rung 1: **3**
(Baumgartner, Bradley & Howard, Coyne). Not applicable: **1** (Baumeister). Only **one study in
ten** touches a raw platform event log with declared semantics — and it is precisely the one
whose reconstruction heuristic is undeclared and whose code is unreleased.

**Availability.** Public analysis data: 3 (Bradley & Howard, Dekker, Cernat's survey half).
Public analysis code: 2 (Andrews' MATLAB descriptives; Cernat's R). **Public
event-to-episode processing code: 0.** Every study that had a reconstruction step released
nothing that would let you re-run it.

**What surprised me.**
1. **Entry 4 (Beierle).** I expected the field's silence to be silence. It is worse: the one
   study operating at Rung 4 openly names its heuristic — background-app removal, event-loss
   detection, imputation of missing events — enumerates the three most consequential choices in
   the entire pipeline, gives not one parameter for any of them, and releases no code. Then it
   reports a 22:1 event-to-session compression as a fact. If the paper needs a single exhibit,
   this is it.
2. **Entry 7 (Cernat).** A *measurement-quality* paper — MTMM, reliability and validity decomposed
   to two decimals — that explicitly writes *"at what threshold does a visit to a website count as
   having engaged with the content"* as a known researcher decision, and then estimates the
   quality of durations whose construction rule it does not possess and cannot inspect, because a
   commercial panel vendor computed them. The multiverse of specifications is being audited one
   layer above the layer that actually generates the numbers.
3. **Entry 10 (Dekker).** The cleanest documented instance of a filter discovered *through its
   output*: two apps (YouTube Vanced, Basic Daydreams) removed because 22-hour days looked wrong,
   with no general criterion — while extreme gaming outliers were kept. And the launcher is
   filtered out of the notification stream but left in the screen-time stream, in the same
   Measures section, without comment.
4. **Entry 8 (Christensen).** Titled *"Direct Measurements of Smartphone Screen-Time"* and
   published with an exemplary, fully-specified rolling-window missingness rule — attached to an
   exposure variable that is minutes-per-hour bins from a vendor SDK, with no event semantics
   stated anywhere. Methodological rigour applied downstream of a measurement whose construction
   is undescribed is a recurring shape in this lane.
